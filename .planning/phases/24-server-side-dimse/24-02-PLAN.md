  <name>Task 1: HandleCMoveAsync with C-STORE forwarding to destination</name>
  <files>
    src/SharpDicom/Network/DicomServer.cs

  <action>
  Implement `HandleCMoveAsync` in DicomServer:

  1. **Read identifier dataset** from subsequent P-DATA PDUs (same pattern as HandleCFindAsync)
  2. **Check handlers**: If `_options.HasCMoveHandler` is false (OnCFind, OnCMoveRetrieve, or OnResolveMoveDestination is null), read+discard dataset, send C-MOVE-RSP with status 0xA900 (Unable to Process) and `SubOperationProgress.Empty`, return.
  3. **Extract MoveDestination** from the QRCommandInfo (already parsed in Plan 01)
  4. **Resolve destination**: Call `_options.OnResolveMoveDestination(moveDestination)`. If null, send C-MOVE-RSP with status 0xA801 (Move Destination Unknown) and return.
  5. **Find matches**: Collect all matches by iterating `_options.OnCFind(identifierDataset, ct)` into a `List<DicomDataset>` (need all matches to know total count for progress). Cap at a reasonable limit (e.g., 10000) to prevent memory exhaustion.
  6. **Open forwarding association**: Create a new `DicomClient` with the resolved host:port. Build presentation contexts for common Storage SOP Classes (or derive from the matches' SOP Class UIDs). Call `ConnectAsync`. Use `try/finally` to ensure `DisposeAsync` is called.
  7. **Forward files via C-STORE sub-operations**:
     - Track: `completed`, `failed`, `remaining` (initialized to match count), `warning` counts
     - For each match:
       - Call `_options.OnCMoveRetrieve(match, ct)` to get DicomFile
       - If file is null, increment `failed`
       - Else: serialize and send C-STORE-RQ on the forwarding association. On success increment `completed`, on exception increment `failed` (per CONTEXT.md: continue sending remaining files)
       - Decrement `remaining`
       - Send intermediate Pending C-MOVE-RSP with `SubOperationProgress(remaining, completed, failed, warning)` on the ORIGINAL association
       - Check cancellation (C-CANCEL): if cancelled, break loop, send Cancel status (0xFE00)
  8. **Send final C-MOVE-RSP**: Status is Success (0x0000) if all succeeded, Warning (0xB000) if some failed, or the failure status if all failed.
  9. **Close forwarding association**: Release the DicomClient connection.

  For the forwarding C-STORE, use the DicomClient's existing store capabilities. The simplest approach:
  - Build the dataset bytes using DicomStreamWriter
  - Use DicomClient.SendDimseAsync or lower-level PDU writing
  - OR: Use CStoreScu for each file (create CStoreScu on the forwarding client)

  CRITICAL per DICOM PS3.4 C.4.2: "C-STORE sub-operations shall always be accomplished over an Association different from the Association that accomplishes the C-MOVE operation." The forwarding association MUST be separate.

  Add well-known status constants to DicomStatus if not present:
  - `MoveDestinationUnknown = new(0xA801)`
  - `SubOperationsCompleteWithFailures = new(0xB000)` (may already exist as CoercionOfDataElements)

  Timeout handling: Use 30s connection timeout, 60s per-operation timeout for the forwarding client. No retry on individual failures per CONTEXT.md.

  Implement `HandleCGetAsync` in DicomServer:

  1. **Read identifier dataset** (same pattern)
  2. **Check handlers**: If `_options.HasCGetHandler` is false, read+discard, send C-GET-RSP with 0xA900 and return.
  3. **Find matches**: Iterate `_options.OnCFind(identifierDataset, ct)` into list (same as C-MOVE)
  4. **Send C-STORE sub-operations on SAME association**:
     - CRITICAL difference from C-MOVE: C-GET sends C-STORE-RQ on the SAME association. The requesting SCU must have accepted SCP role for Storage SOP Classes (role selection).
     - For each match:
       - Call `_options.OnCGetRetrieve(match, ct)` to get DicomFile
       - Build C-STORE-RQ command using `DicomCommand.CreateCStoreRequest`
       - Serialize command + dataset
       - Send as P-DATA PDVs on the SAME stream (using the existing association's presentation context for the Storage SOP Class)
       - Read C-STORE-RSP from the SCU (the SCU acts as SCP for these C-STORE sub-ops)
       - Track completed/failed/remaining/warning based on response status
       - Send intermediate Pending C-GET-RSP using `DicomCommand.CreateCGetResponse` with `SubOperationProgress`
       - Check C-CANCEL: break if cancelled
  5. **Send final C-GET-RSP**: Same status logic as C-MOVE.

  Key implementation detail for same-association C-STORE:
  - Need to find the right presentation context ID for the Storage SOP Class of the instance being sent. Check `association.GetAcceptedContextForAbstractSyntax(sopClassUid)` or iterate accepted contexts to find one matching the SOP Class UID.
  - If no matching context is accepted (SCU didn't propose Storage SOP Class with SCP role), skip this instance and increment `failed`. Per RESEARCH.md Open Question 2.

  For reading C-STORE-RSP back from the SCU:
  - After sending C-STORE-RQ with dataset, read the next P-DATA PDU which should contain the C-STORE-RSP command
  - Parse command field to confirm it's 0x8001 (C-STORE-RSP) and extract status

  Wire HandleCMoveAsync and HandleCGetAsync into HandlePDataAsync:
  - Replace the Plan 01 stubs (which returned 0xA900) with actual calls to HandleCMoveAsync and HandleCGetAsync

  - C-GET: commandField == 0x0010
